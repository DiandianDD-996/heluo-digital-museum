软件测试课程期末大作业 · 首轮实机与业务测试 · V1.0

### 4.1 前端和后端怎样一起测

前端检查“能否显示和操作”；后端检查“是否合法、是否保存、是否隔离、是否只执行一次”。每条业务线至少保留一条正常请求和一条异常或权限请求的证据，PC 端即可，不要求成员安装工具。

愿意操作的成员可按 F12 → Network（网络）→ Fetch/XHR，清空列表后执行一次动作，记录请求方法、去掉敏感参数的地址、状态码、耗时和响应的业务提示。不要截图 Authorization、Cookie 或密码请求体，也不提交完整 HAR 文件。

HTTP 200 仅说明请求得到响应，仍要检查业务内容；HTML 外壳也可能是 200。输入错误应被拒绝且无错误写入，未认证应拒绝、越权应拒绝且无数据泄露。只被前端挡住的输入，服务端校验由组长在隔离环境补测。

### 7.1 和 D 的边界

个人中心外壳、资料和预约由 C 主测；订单列表、支付和取消由 D 主测。D 发现个人中心整体布局问题时交 C 汇总，仍保留发现设备与截图。C 负责完整注册验证，其他成员只完成自己业务所需登录和退出。

最少证据：一次注册登录记录、一个预约从创建到后台确认或取消的完整编号链路、手机键盘下的预约表单截图。邮件未配置必须单列，不归咎为已经确认的代码故障。

| D02 | 指定测试商品加入购物车，增加/减少数量、移除；关闭后重开及刷新 | 数量、选中状态与合计一致；空车有提示，不重复加入成错误记录 |
| D03 | 分别测试数量 0/1/10/11 和超过剩余库存 | 当前数量规则 1—10 且不超过可用库存；非法数量被拒绝，不把非法状态保存 |
| D04 | 选择指定商品创建订单；比较购物车、确认金额和订单明细 | 只结算选中商品；订单数量、单价、合计正确，得到唯一待支付订单编号 |
| D05 | 完成一次模拟支付，刷新后在个人中心和后台核对 | 同一订单成为已支付，金额不变，库存只扣一次；实际通知收到与否单独记录 |
| D06 | 在允许的测试场景短暂双击支付一次；恢复后查看订单 | 不重复生成订单、支付记录或重复扣库存；组长用接口证据补验幂等 |
| D07 | 对专用待支付订单模拟断网/请求失败，恢复网络后查看并继续支付 | 先核对是否已支付，未支付才重试；可恢复同一订单，不被迫重复下单 |
| D08 | 取消一个待支付订单；另一个专用订单等待 30 分钟以上再刷新 | 合法取消释放锁定库存；超时订单自动取消且不能再支付，记录创建与检查时间 |
| D09 | 与组长核对商品下架/价格变化，后台完成已支付订单，再看历史记录 | 下架不能新购；历史订单快照不随商品改价改变；订单完成状态前后台一致 |

不要把购物车展示价当成最终结算承诺。若下单前价格变化，核对创建时后端返回的最终金额及页面提示；下单后历史金额不应再随商品价格变化。库存与下架场景仅在指定测试商品/隔离环境操作。

最少证据：一个“加入购物车→下单→模拟支付→个人中心→后台”的订单编号链路；一次失败/重试记录；手机购物车和结算截图。30 分钟过期可在其他检查期间自然等待，不需持续盯屏。

入口：`/admin`、`/admin/operations`。下面涉及状态修改的用例只针对隔离环境和本组测试数据。组长操作管理端，成员在普通用户或游客端核对，约两个 45 分钟联测窗口即可集中完成。

| L08 | 对非法字段和越权请求记录响应；对重复创建/支付使用同一幂等键复验 | 错误输入不入库，403/404 不泄露对象；重复请求返回同一业务结果，只产生一次作用 |
| L09 | 隔离环境两账号争最后一个名额/库存；测试已取消订单再次支付 | 不超额、不超卖、不重复扣减；终态不能非法回退，保留操作前后数量 |
| L10 | 后台 PC 表单、列表筛选、分页、错误恢复及手机/平板关键操作巡检 | 关键列和按钮可到达，保存失败保留可恢复输入；共享控件按 G 项验收 |

## 11 响应速度与稳定性怎么记录

目标是回答“在什么设备和网络下，哪个动作慢了多久”，不只写“挺流畅”。每人至少测两个动作，在 PC 和手机分别记录；普通读取或页面跳转重复三次，写操作只观察自然产生的不同测试记录，不为凑次数重复下单。

| 类型 | 从哪里开始计时 | 到哪里结束计时 |
|---|---|---|
| 页面可用 | 点击页面入口或确认网址 | 主内容显示，主要按钮能操作 |
| 搜索结果 | 点击搜索或最后一次输入触发搜索 | 正确结果或无结果提示稳定显示 |
| 表单提交 | 点击注册/预约/下单/支付 | 明确成功或失败提示；编号/状态可核对 |
| 3D 可操作 | 点击进入 3D 展项 | 模型出现且实际拖拽能旋转 |

可用手机录屏时间轴或秒表估算到 0.1 秒；这属于用户感知耗时，含网络、服务端和渲染。Network 的接口耗时另记，不能互相替代。每条记录写上“秒表/录屏/Network”及“首次访问/重复访问”。

测量步骤：记录设备、浏览器、网络和时间；首次打开单独记一次；应用已可用后做三次正常读取，记录三个原值并取中位数。例如 1.2、2.8、1.5 秒，中位数为 1.5 秒。手机另用移动数据复测一个读取动作，不要求全员全场景切网。

### 11.1 本轮体验排查参考

以下是小组建议的调查线，不是老师标准、性能承诺，也不替代 N-04 本机接口指标。超过调查线先复测并结合设备/网络分析，不直接认定后端故障。

| 动作 | 建议关注线 | 记录重点 |
|---|---|---|
| 点击反馈或出现加载提示 | 约 1 秒内应可见 | 是否让人误以为没点到而重复点击 |
| 普通页面可用 | 应用已启动、正常网络下约 3 秒 | 三次耗时、主要内容何时可用 |
| 搜索/业务操作结果 | 正常网络下约 3 秒 | 写操作单次如实记录，是否持续超过 5 秒 |
| 3D 首次可操作 | 超过 10 秒重点记录 | 加载说明是否持续有效；30 秒仍不可用记录加载失败/阻塞现象 |
| 连续使用 | 3 分钟操作，5 次进出 | 卡顿频率、闪退、明显发热；无需估算专业帧率 |

平台休眠/唤醒时间单列，例如“入口等待 40 秒，应用就绪后页面 2 秒”，不要混入正常三次中位数。若看到托管提示、空白页或只有平台外壳，截图并报告组长；不要把外壳 HTTP 200 当作博物馆功能通过。30 秒仍不可测即可记录阻塞，组长可继续调查。

手机省电模式、浏览器后台切回、Wi-Fi 信号、首次模型缓存都会影响结果；记录条件即可，不要求统一高端设备。系统性能指标和长时间稳定性未测时明确保留。

## 12 缺陷反馈和首轮验收

每个问题一个编号，例如 `BUG-C-001`。写清发生在哪个页面、设备、账号角色、怎样重现、原本应该怎样、实际怎样，并附截图或短录屏。先描述现象，归因可写“待定位”，不必猜前端还是后端。

| 程度 | 例子 | 处理方式 |
|---|---|---|
| 严重 | 越权看到他人资料；重复支付/库存错误；核心流程普遍无法完成 | 发现即联系组长，保留证据，停止扩大影响的操作 |
| 一般 | 某设备预约按钮被挡；部分模型无法加载；搜索结果错误 | 当天登记，首版提交前请同学复现 |
| 轻微 | 不影响操作的间距、错别字、非关键对齐问题 | 放入首版，附清晰位置截图 |

### 12.1 交付要求

复制 `02-个人首轮测试反馈模板.docx`，用 Word 或 WPS 直接填写，不用排新格式。不需要写长篇测试理论；通过项一行即可，失败项写问题卡，阻塞项写缺什么条件。

文件命名：`河洛测试反馈_姓名_模块_20260918_v1.docx`。截图放入同名证据文件夹，可连同文档打包为 ZIP。例：`BUG-C-001_手机预约按钮.png`。录屏建议 15—45 秒，能看清步骤即可；联系方式打码。

每人提交前自查：

- 姓名、设备、浏览器版本、网络和测试时间已填。
- G 组及自己负责用例在 PC/手机都有结果；每个未覆盖设备/子项注明原因。
- 至少一条核心流程从入口到最终记录验证；已与组长核对关联编号或明确联测阻塞。
- 每个失败项有缺陷编号、步骤、预期、实际、证据；偶发问题写复现次数。
- 两个动作的速度记录完整；读操作保留三次原值，写操作不足三次注明未重复执行。
- 即使没发现问题也提交反馈；不空交、不把未测写通过、不要求凑缺陷数。

### 12.2 组长如何收口

将四份报告合并去重，保留原缺陷编号和发现者。为每个问题指定修复人、状态“待确认/待修复/待复测/已关闭”，严重问题先处理。修复后由原发现者按原设备、原步骤复测，再补一条正常主流程；仍复现则退回修复。

| 汇总项 | 组长填写 |
|---|---|
| 收到首版 | A ___　B ___　C ___　D ___ |
| 必测记录数 | 应测 ___；通过 ___；失败 ___；阻塞 ___；未测 ___；批准不适用 ___ |
| 有效独立问题 | 严重 ___；一般 ___；轻微 ___；重复合并 ___ |
| 覆盖与缺口 | 实机/浏览器 ___；缺失设备 ___；邮件/隔离环境 ___ |
| 回归安排 | 修复负责人 ___；候选版本 ___；回归日期 ___ |

若统计，通过率＝通过÷（通过＋失败）；执行覆盖率＝（通过＋失败）÷（应测－批准不适用）。应测按“用例或子项×适用设备”计数，阻塞/未测留在覆盖率分母；分母为零写“不可计算”。用同一粒度统计，不能只报漂亮的通过率。

首轮完成是“反馈可用、证据可复现、缺口已列出”，不等于网站全部通过。课程最终材料建议保留任务书、个人报告、缺陷汇总、修复前后证据及测试总结，方便展示每位成员贡献。
